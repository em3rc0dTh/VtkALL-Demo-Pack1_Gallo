# ADR-001 — Temporal como orquestador central de Demo Test / Pack 0

**Estado:** Propuesto
**Fecha:** 2026-07-03
**Rama sugerida:** `arch/adr-001-demo-test-temporal-pack-0`
**Ámbito:** `demo_test` → VtkALL Demo Pack 0
**Decisores:** Equipo VertikALL / Thradex

## Contexto

`demo_test` será el laboratorio arquitectónico donde VtkALL valida el uso de Temporal como motor de orquestación durable antes de madurar hacia **VtkALL Demo Pack 0**.

El alcance inicial cubre los siguientes casos de uso:

* **USE-02:** Registro de cliente.
* **USE-03:** Registro de entidad gestionada.
* **USE-04:** Crear caso operativo.
* **USE-05:** Agendar cita o consulta.

El modelo de datos vigente es **v3 timeslots**, que incorpora `WorkTeam`, `WorkTeamScheduleRule`, `WorkTeamScheduleOverride` y `ResourceReservation` como base de disponibilidad y reserva operacional.

MongoDB se mantiene como fuente de verdad persistente. Backend/API conserva las reglas de dominio, validaciones transaccionales y escritura en base de datos. Temporal gobierna el flujo, esperas, señales, reintentos, compensaciones y continuidad del proceso.

El agente IA o consola manual no decide reglas de negocio. Solo presenta instrucciones, recolecta datos, solicita confirmaciones y envía comandos estructurados al Backend/API o señales al workflow correspondiente.

## Decisión

Adoptamos **Temporal como orquestador central de procesos** para `demo_test`, sin convertirlo en capa de dominio ni en fuente de verdad persistente.

La arquitectura base queda definida así:

```text
Agente IA / Consola Manual
        ↓
Backend/API — reglas de dominio + persistencia transaccional
        ↓
MongoDB — fuente de verdad persistente
        ↑
Temporal Activities — operaciones atómicas contra Backend/API
        ↑
Temporal Workflows — orquestación durable del proceso
```

Temporal coordina el flujo completo, pero no reemplaza al Backend/API.

## Decisiones arquitectónicas congeladas

### 1. Temporal gobierna el flujo, no el dominio

Temporal será responsable de:

* iniciar y continuar workflows;
* esperar señales humanas o del agente;
* manejar timers, expiraciones y reintentos;
* coordinar Activities;
* registrar puntos de avance;
* ejecutar compensaciones cuando una operación falle parcialmente.

Temporal no será responsable de:

* validar reglas de negocio finales;
* escribir directamente en MongoDB;
* calcular disponibilidad sin pasar por servicios de dominio;
* decidir transiciones inválidas de estado;
* actuar como repositorio primario del sistema.

### 2. Backend/API conserva reglas de dominio y persistencia

Backend/API seguirá siendo la capa dueña de:

* creación y actualización de `Customer`;
* creación y actualización de `ManagedEntity`;
* creación y actualización de `Case`;
* creación de `Appointment`;
* cálculo de disponibilidad;
* creación de `ResourceReservation`;
* validación de estados;
* escritura de `TimelineEvent`;
* validaciones de integridad;
* persistencia transaccional en MongoDB.

Toda Activity de Temporal que modifique estado persistente debe llamar a un servicio del Backend/API o reutilizar directamente la misma capa de dominio del Backend, nunca duplicar reglas dentro del workflow.

### 3. MongoDB es la fuente de verdad

MongoDB será la fuente persistente oficial para:

* `Customer`;
* `ManagedEntity`;
* `Case`;
* `Appointment`;
* `WorkTeam`;
* `WorkTeamScheduleRule`;
* `WorkTeamScheduleOverride`;
* `ResourceReservation`;
* `TimelineEvent`;
* entidades futuras de Pack 0.

El historial de Temporal sirve para durabilidad y trazabilidad técnica del workflow, pero no sustituye a MongoDB como fuente consultable del producto.

### 4. El agente IA y la consola manual son interfaces, no autoridad de negocio

El agente IA o la consola manual pueden:

* hacer preguntas al usuario;
* recolectar datos;
* sugerir próximos pasos;
* mostrar disponibilidad;
* solicitar confirmación;
* enviar comandos estructurados;
* emitir señales a Temporal.

No pueden:

* saltarse validaciones del Backend/API;
* reservar capacidad directamente;
* crear casos sin pasar por servicio de dominio;
* alterar estados fuera de la máquina permitida;
* asumir aprobación sin evidencia;
* escribir en MongoDB directamente.

### 5. El modelo raíz es Case, no Cita

Pack 0 debe consolidar la tesis de que VtkALL no modela solamente citas.

La raíz operativa será:

```text
Customer → ManagedEntity → Case → Appointment/Consultation → Timeline
```

Para el alcance inicial:

```text
USE-02 Customer
USE-03 ManagedEntity
USE-04 Case
USE-05 Appointment + ResourceReservation
```

`Cita` o equivalentes legacy pueden existir como compatibilidad, pero no deben guiar el diseño nuevo de `demo_test`.

### 6. Appointment agenda; ResourceReservation bloquea capacidad

`Appointment` representa la cita o consulta visible para el cliente.

`ResourceReservation` representa el bloqueo real de capacidad del equipo.

La disponibilidad se calcula desde:

```text
WorkTeam
+ WorkTeamScheduleRule
+ WorkTeamScheduleOverride
+ ResourceReservation
```

`AvailabilitySlot` puede mantenerse para compatibilidad temporal, demos antiguas o Postman, pero no será fuente futura de verdad.

### 7. USE-05 debe ser transaccional desde el punto de vista del dominio

Agendar una cita o consulta requiere, como mínimo:

```text
1. Validar Customer.
2. Validar ManagedEntity.
3. Validar Case.
4. Calcular disponibilidad.
5. Crear ResourceReservation en estado held o booked.
6. Crear Appointment asociado a esa reserva.
7. Registrar TimelineEvent.
8. Devolver resultado al workflow.
```

Si falla la creación de `Appointment` después de bloquear capacidad, el sistema debe liberar o marcar la reserva como `released`.

Si falla la reserva, no debe crearse una cita confirmada.

### 8. Los workflows iniciales de demo_test serán pequeños y componibles

No se implementará un mega-workflow.

Para Pack 0 se congelan estos workflows iniciales:

```text
CustomerRegistrationWorkflow
ManagedEntityRegistrationWorkflow
OperationalCaseWorkflow
ScheduleConsultationWorkflow
```

El flujo mínimo compuesto será:

```text
RegisterCustomer
→ RegisterManagedEntity
→ CreateOperationalCase
→ ScheduleConsultation
```

Cada paso invoca Activities que delegan en servicios de dominio.

### 9. Las Activities son comandos de aplicación

Las Activities deben expresar operaciones de negocio atómicas:

```text
createOrUpdateCustomerActivity
createManagedEntityActivity
createOperationalCaseActivity
calculateAvailabilityActivity
holdResourceReservationActivity
confirmResourceReservationActivity
createAppointmentActivity
recordTimelineEventActivity
releaseResourceReservationActivity
```

Las Activities no deben contener lógica de orquestación larga. Esa lógica vive en el workflow.

### 10. TimelineEvent será el puente entre negocio y trazabilidad

Todo cambio importante del flujo debe registrar un `TimelineEvent`.

Eventos mínimos para ADR-001:

```text
customer.created
managed_entity.created
case.created
availability.checked
resource_reservation.held
resource_reservation.booked
appointment.scheduled
appointment.confirmed
appointment.failed
resource_reservation.released
status.changed
```

Temporal registra el historial técnico; `TimelineEvent` registra la historia de negocio visible y auditable.

## Contrato mínimo de ejecución

### Flujo nominal

```text
1. El agente o consola recolecta datos mínimos.
2. Se inicia workflow en Temporal.
3. Temporal llama Activity para registrar Customer.
4. Backend/API valida y persiste Customer en MongoDB.
5. Temporal llama Activity para registrar ManagedEntity.
6. Backend/API valida y persiste ManagedEntity.
7. Temporal llama Activity para crear Case.
8. Backend/API valida y persiste Case.
9. Temporal llama Activity para calcular disponibilidad.
10. Backend/API calcula disponibilidad con WorkTeam + rules + overrides + reservations.
11. Temporal llama Activity para reservar capacidad.
12. Backend/API crea ResourceReservation.
13. Temporal llama Activity para crear Appointment.
14. Backend/API crea Appointment asociado a ResourceReservation.
15. Backend/API registra TimelineEvent.
16. Workflow finaliza o queda esperando confirmación.
```

### Flujo con fallo de reserva

```text
1. Se intenta reservar capacidad.
2. Backend/API detecta conflicto de slot.
3. No se crea Appointment.
4. Temporal solicita nuevas opciones o termina con error controlado.
```

### Flujo con fallo posterior a reserva

```text
1. Se crea ResourceReservation.
2. Falla la creación de Appointment.
3. Temporal ejecuta compensación.
4. Backend/API marca ResourceReservation como released.
5. Se registra TimelineEvent de fallo.
```

## Consecuencias

### Positivas

* Pack 0 nace con separación clara entre orquestación, dominio y persistencia.
* `demo_test` puede evolucionar sin romper Pack 1 ni Pack 2.
* Temporal permite procesos durables con esperas, reintentos y compensaciones.
* MongoDB conserva la fuente de verdad consultable por frontend, dashboards y reportes.
* Backend/API sigue siendo el lugar correcto para reglas transaccionales.
* El agente IA queda limitado a interacción y captura, reduciendo riesgo de inconsistencias.
* El modelo v3 timeslots queda protegido desde el inicio.

### Negativas o costos

* Hay más piezas que un CRUD simple.
* Requiere disciplina para no duplicar reglas dentro de Workflows o Activities.
* Requiere definir contratos claros entre Temporal y Backend/API.
* Requiere pruebas de idempotencia para Activities.
* Requiere modelar compensaciones desde el primer flujo de agenda.

## Reglas de implementación

1. Toda Activity que escriba datos debe ser idempotente.
2. Todo comando debe incluir `businessSlug`.
3. Todo `Case` debe tener `customerId`.
4. Toda `ManagedEntity` debe pertenecer a un `Customer`.
5. Toda cita con horario debe tener `ResourceReservation`.
6. Solo reservas `held` o `booked` bloquean capacidad.
7. Toda transición relevante debe generar `TimelineEvent`.
8. Temporal no escribe directamente en MongoDB.
9. El agente no escribe directamente en MongoDB.
10. Backend/API valida antes de persistir.
11. El workflow puede decidir el siguiente paso, pero no puede saltarse reglas de dominio.
12. `AvailabilitySlot` queda como compatibilidad legacy, no como fuente futura de disponibilidad.

## Fuera de alcance de ADR-001

Este ADR no define todavía:

* cotizaciones;
* diagnósticos;
* factibilidad;
* WorkOrders;
* pagos;
* PDFs;
* WhatsApp real;
* multitenancy SaaS formal;
* separación de bases de datos por cliente;
* Pack 1 o Pack 2 en producción.

Esas decisiones deberán congelarse en ADRs posteriores.

## Criterio de aceptación

ADR-001 se considera cumplido cuando `demo_test` puede ejecutar el siguiente flujo mínimo:

```text
Registrar cliente
→ Registrar entidad gestionada
→ Crear caso operativo
→ Calcular disponibilidad
→ Crear ResourceReservation
→ Crear Appointment
→ Registrar TimelineEvent
```

Y cuando se pueda demostrar que:

```text
- MongoDB contiene el estado persistente final.
- Temporal contiene el historial durable del workflow.
- Backend/API aplicó las reglas de dominio.
- El agente o consola solo actuó como interfaz.
- No existe doble reserva para el mismo equipo y micro-slot bloqueante.
```

## Decisión final

Se aprueba que **VtkALL Demo Test / Pack 0 use Temporal como orquestador central**, manteniendo **Backend/API como dueño del dominio**, **MongoDB como fuente de verdad persistente**, y **v3 timeslots como base oficial de agenda y capacidad operacional**.

Esta decisión congela la arquitectura mínima para que `demo_test` madure hacia Pack 0 sin contaminar ni romper los alcances existentes de Pack 1 y Pack 2.
